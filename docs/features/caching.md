# Semantic Caching Layer

Vortex integrates a local, **zero-cost Semantic Caching layer** based on vector similarity. This layer stores previously generated responses and yields them instantly when a user asks a semantically equivalent query.

---

## 💡 Why Semantic Caching?

1.  **Reduce Token Costs**: Prevents repeating expensive LLM calls for frequent or slightly rephrased questions.
2.  **Mitigate Rate Limits**: Bypasses external API boundaries completely for cached questions.
3.  **Low Latency**: Bypasses the entire LangGraph workflow execution, resolving queries in milliseconds instead of seconds.

---

## 🛠️ Zero-Cost Local Implementation

To maintain a zero-cost stack, the semantic cache does not require Redis or cloud resources:
*   **Vector Collection**: Utilizes a dedicated ChromaDB collection named `vortex_semantic_cache` stored alongside the primary vector index in `data/chroma_db`.
*   **Embeddings Model**: Reuses the shared, local HuggingFace `sentence-transformers/all-MiniLM-L6-v2` instance, meaning no additional memory overhead or model loading delay.
*   **Distance Metric**: Configured with cosine distance (`hnsw:space: cosine`). The similarity threshold is adjustable (default `0.1`, which translates to `>90%` similarity).

---

## 🔒 Provider Partition Isolation

To prevent returning a response generated by one model provider to a client executing a different provider, the cache collection partitions entries:
*   Entries are tagged with `provider` metadata.
*   Lookup queries apply a metadata filter ensuring only matches from the *active provider* are checked.

---

## 🔄 Caching Flow

The cache hooks directly into the FastAPI endpoint:

```
[User Request]
       │
       ▼
 [Cache Lookup] ──(HIT)──► [Reconstruct ChatResponse] ──► [Return to User]
       │
    (MISS)
       │
       ▼
 [Execute LangGraph]
       │
[Generation Success]
       │
       ▼
  [Cache Update] ──► [Store Query, Response, Sources & Steps]
```

### Metadata Serialization
When a cache entry is written, complex state objects (like list of documents with metadata, and executed steps) are serialized into JSON strings and stored in the database. When a cache hit occurs, these JSON strings are parsed to reconstruct the complete `ChatResponse` model, including all citations and steps. The step list is appended with `"semantic_cache_hit"` for transparency.

---

## ⚙️ Configuration Parameters

The caching behavior is governed by environment variables in `.env`:

```env
# Enable or disable semantic caching (default: true)
ENABLE_SEMANTIC_CACHE=true

# Cosine distance threshold. Lower means stricter matching (default: 0.1)
SEMANTIC_CACHE_THRESHOLD=0.1
```
